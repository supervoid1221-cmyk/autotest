# 测试平台后端：模块与使用说明

## 1. 平台概览

这是一个基于 **Django 4.2 + Django REST Framework（DRF）** 的测试管理后端。平台将项目、接口测试、UI 自动化测试和测试套件统一管理；执行套件时会把平台中的用例转换为 YAML，再调用内置的 pytest 框架运行，并产出原生报告、日志和执行产物。

主要流程如下：

```text
账号/组织 → 项目 → 接口或 UI 用例 → 测试套件 → 运行记录 → 报告/日志/产物
```

所有业务接口以 `/api/` 开头。DRF 的标准资源接口均支持：

| 操作 | HTTP 方法 | URL 形式 |
| --- | --- | --- |
| 列表 | GET | `/资源/` |
| 新建 | POST | `/资源/` |
| 详情 | GET | `/资源/{id}/` |
| 全量修改 | PUT | `/资源/{id}/` |
| 局部修改 | PATCH | `/资源/{id}/` |
| 删除 | DELETE | `/资源/{id}/` |

返回结果由全局渲染器统一封装为 `code`、`message`、`result` 三个字段；分页列表的 `result` 中包含 `itemCount`、`next`、`previous`、`list`。分页参数为 `page` 与 `pageSize`。

## 2. 运行与文档入口

### 环境准备

项目要求 Python 3.10 及以上。依赖记录在 `requirements.txt` / `pyproject.toml` 中，包含 Django、DRF、Selenium、pytest、django-q2 等。

```bash
python3 -m pip install -r requirements.txt
python3 manage.py migrate
python3 manage.py runserver
```

如需启用 Cron 定时套件，还[settings.py](Tesla%2Fsettings.py)应在另一终端启动 django-q2 集群：

```bash
python3 manage.py qcluster
```

### 接口文档与后台

| 功能 | 地址 |
| --- | --- |
| Swagger UI | `/api/schema/swagger/` |
| ReDoc | `/api/schema/redoc/` |
| OpenAPI JSON | `/api/schema/openapi.json` |
| Django 管理后台 | `/admin_by_127_0_0_1/` |

默认使用 SQLite 数据库文件 `db.sqlite3`。生产部署时应替换密钥、关闭 `DEBUG`、收紧 `ALLOWED_HOSTS` 和跨域策略，并改用合适的数据库与静态文件服务。

## 3. 模块说明

### 3.1 账号模块（`account`）

负责登录、个人资料、密码修改、头像上传及用户列表查询。登录成功会自动补齐 `Profile` 和 DRF Token。

基础地址：`/api/account/profile/`

| 接口 | 方法 | 用途 |
| --- | --- | --- |
| `login/` | POST | 用户名密码登录，返回用户资料、角色和 Token |
| `profile/` | GET | 获取当前登录用户资料 |
| `change/` | POST | 更新当前用户资料 |
| `reset_password/` | POST | 修改当前用户密码 |
| `img_upload/` | POST | 上传当前用户头像文件 |
| `all_user/` | GET | 查询所有用户资料 |

登录请求示例：

```json
{"username": "admin", "password": "your-password"}
```

修改密码请求示例：

```json
{"new_password": "new-password", "confirm_password": "new-password"}
```

除登录外，调用方应通过 `Authorization: Token <token>` 提供令牌；Token 认证已配置为默认认证方式。头像上传使用 `multipart/form-data`，文件字段为 `img`。头像静态访问路径为 `/api/account/static/...`。

### 3.2 组织与角色模块（`system`）

管理部门、职位和用户角色，供账号资料展示其所属组织和是否为负责人。

| 资源 | 基础地址 | 关键字段 |
| --- | --- | --- |
| 部门 | `/api/system/department/` | `name`、`intro`、`leader`（用户 ID） |
| 职位 | `/api/system/position/` | `name`、`is_leader` |
| 角色 | `/api/system/role/` | `user`、`department`、`position` |

角色列表接口会额外返回部门名称、职位详情和用户资料，便于组织人员页面直接展示。

### 3.3 项目管理模块（`project`）

项目是接口、UI 用例和测试套件的归属边界。

| 资源 | 基础地址 | 关键字段/用途 |
| --- | --- | --- |
| 项目 | `/api/project/project/` | `name`、`intro`、`url`、`user_list`、`pm` |
项目负责人 `pm` 和成员 `user_list` 均引用 Django 用户 ID；项目详情中会补充负责人资料 `pm_profile`。

### 3.4 接口测试模块（`case_api`）

该模块先维护接口定义，再基于接口创建接口测试用例。执行套件时，用例会导出为 pytest 框架可识别的 YAML 文件。

| 资源 | 基础地址 | 关键字段 |
| --- | --- | --- |
| 接口定义 | `/api/case_api/endpoint/` | `name`、`project`、`method`、`url`、`params`、`data`、`json`、`cookies`、`headers` |
| 场景与接口步骤 | `/api/case_api/scenario/`、`/api/case_api/scenario-step/` | 场景关联项目；步骤直接选择该项目下的接口，并可覆盖参数、配置数据提取与断言 |

使用方式：

1. 创建接口定义，填写请求方法、URL 以及通用请求参数。
2. 创建接口用例并关联该接口；`api_args` 可按请求字段覆盖或补充接口定义。
3. 填写数据提取规则 `extract` 与断言规则 `validate`。
4. 将用例加入测试套件后执行。

导出的 YAML 结构以 `test_name`、`request`、`extract`、`validate` 为核心。运行框架支持 `equals` 和 `contains` 两类断言，且会把提取到的数据写入共享的 `extract.yaml`，可供后续用例模板替换使用。

### 3.5 UI 自动化模块（`case_ui`）

用于管理页面元素、UI 用例和有序操作步骤。套件执行时，平台生成独立 UI YAML，由 Selenium 执行器运行并把步骤状态、页面信息、断言和错误写入原生报告。

| 资源 | 基础地址 | 关键字段 |
| --- | --- | --- |
| UI 元素 | `/api/case_ui/element/` | `name`、`project`、`by`、`value` |
| UI 用例 | `/api/case_ui/case/` | `name`、`project`、`browser`、`run_mode`、`tabs`、`enabled` |
| UI 步骤 | `/api/case_ui/step/` | `ui_case`、`tab_key`、`order`、`action`、`element`、`value`、`options` |

元素的 `by` 为 Selenium 定位方式（如 `ID`、`NAME`、`XPATH`、`CSS_SELECTOR`），`value` 是定位表达式。

UI 用例通过 `/api/case_ui/case/{id}/sync-steps/` 原子保存步骤及顺序。步骤示例：

```json
{
  "order": 1,
  "tab_key": "tab-1",
  "name": "打开登录页",
  "action": "goto",
  "element": null,
  "value": "/login",
  "options": {},
  "continue_on_failure": false
}
```

`tabs` 格式为 `[{"key":"tab-1","name":"登录页","order":1}]`。编辑页按 Tab 分组管理步骤，保存时按“Tab 从左到右、Tab 内从上到下”生成全局 `order`；执行 YAML 和原生报告会同时记录 `tab_key` 与 `tab_name`。

编辑页当前支持 `goto`、`click`、`input`、`clear`、`assert_text`、`assert_value`、`iframe_enter`、`iframe_exit`、`select`、`js_code`、`sleep`；后端仍保留 `save_text` 仅用于兼容历史用例。操作值优先使用 `${变量名}`，并兼容 `{{变量名}}`。当前由 `fullstack_framework/commons/ui_executor.py` 统一启动 Chrome，`run_mode` 可设为 `headless`（无头）或 `headed`（有界面），不再依赖 Excel、pytest-xlsx 或全局浏览器 fixture。

### 3.6 测试套件与执行结果模块（`suite`）

测试套件将接口业务场景和 UI 用例编排为一次可执行任务。两类内容使用同一个执行队列，可交错拖拽排序，实际执行与原生报告均严格遵循该顺序。

| 资源 | 基础地址 | 用途 |
| --- | --- | --- |
| 测试套件 | `/api/suite/suite/` | 维护用例集合与触发方式 |
| 执行记录 | `/api/suite/run_result/` | 查询执行状态、报告、日志及产物 |

套件的主要字段：

| 字段 | 说明 |
| --- | --- |
| `environment` | 套件默认执行环境 ID，套件归属由环境项目确定 |
| `execution_items` | 统一执行队列，每项为 `{type: "api"|"ui", id, order}` |
| `scenarios` | 兼容字段，套件关联的接口业务场景 ID 列表 |
| `ui_cases` | 兼容字段，套件关联的 UI 用例 ID 列表 |
| `enabled` | 是否允许执行；停用后不会保留 Cron 调度 |
| `run_type` | `O` 单次、`C` Cron、`W` WebHook |
| `cron` | Cron 表达式，仅 `C` 使用 |
| `hook_key` | WebHook 密钥；首次保存 WebHook 套件时自动生成 |

混合顺序通过 POST `/api/suite/suite/{id}/sync-execution-items/` 保存，请求体为 `{"items": [{"type": "api", "id": 1}, {"type": "ui", "id": 2}]}`。旧的 `sync-scenarios` 与 `sync-ui-cases` 接口仍保留兼容。

触发方式：

| 场景 | 方法与地址 | 说明 |
| --- | --- | --- |
| 手动执行 | POST `/api/suite/suite/{id}/run/` | 仅适用于 `run_type=O` |
| WebHook 执行 | POST `/api/suite/suite/{id}/webhook/` | 仅适用于 `run_type=W`，必须使用请求头签名 |
| 定时执行 | 配置 `run_type=C` 和 `cron` | 由 django-q2 调度，需要运行 qcluster |

执行成功受理后会返回 `result_id`。轮询 `GET /api/suite/run_result/{result_id}/` 可获取状态、是否通过以及以下链接：

WebHook 请求必须携带以下请求头，时间戳使用 Unix 秒，Nonce 应为每次请求新生成的 8～128 位随机字符串：

| 请求头 | 内容 |
| --- | --- |
| `X-Webhook-Key` | 套件的 `hook_key` |
| `X-Webhook-Timestamp` | Unix 秒时间戳，默认仅允许服务器时间前后 5 分钟 |
| `X-Webhook-Nonce` | 仅使用一次的随机字符串 |
| `X-Webhook-Signature` | HMAC-SHA256 十六进制签名 |

签名密钥为 `hook_key`。待签名文本为 `POST`、请求路径、时间戳、Nonce、原始请求体 SHA256 摘要，以换行符连接：

```text
POST
/api/suite/suite/{id}/webhook/
{timestamp}
{nonce}
{sha256(raw_body)}
```

同一个套件的 Nonce 只能成功使用一次；签名错误、过期或重复请求不会启动任务。`?key=` URL 参数和 GET 调用均不再支持。

| 字段 | 内容 |
| --- | --- |
| `log_url` | pytest 日志 |
| `artifacts_url` | 本次执行生成文件的 ZIP 包 |

运行目录创建在 `upload_yaml/result_{记录ID}_{时间戳}` 下，包含由平台生成的 API/UI YAML、报告、日志和 `artifacts.zip`。

## 4. 推荐使用顺序

1. 通过管理后台创建 Django 用户，或使用已有用户登录。
2. 在组织模块配置部门、职位和角色（如需权限/人员展示）。
3. 创建项目，并按需配置项目参数、环境与认证。
4. 维护接口定义和接口用例，或维护 UI 元素与 UI 用例。
5. 创建测试套件，选择同项目的接口用例、UI 用例及运行方式。
6. 手动、定时或 WebHook 触发套件。
7. 查询执行记录，打开原生报告、日志或下载产物。

## 5. 实现现状与接入注意事项

- 当前 REST 默认权限配置为空，绝大多数资源接口未强制鉴权；接入生产前应补充 `IsAuthenticated`、项目级数据隔离和角色权限校验。
- 当前配置允许所有来源跨域，且 `DEBUG=True`、`ALLOWED_HOSTS=["*"]`，仅适合开发环境。
- WebHook 接口无需用户登录，但强制校验请求头 Hook Key、时间戳、Nonce 和 HMAC-SHA256 签名；仍应妥善保管 `hook_key`，生产环境可额外增加网关 IP 白名单。
- UI 自动化依赖可用的 Chrome/ChromeDriver 与目标页面网络条件；默认使用无头模式，有界面模式要求执行任务的机器存在可用桌面会话。
- `fullstack_framework/main_by_django.py` 使用 `Tesla.settings` 启动 Django，并通过运行记录 ID 把 API/UI 步骤结果实时写入原生报告。
