# 调度层水平扩展改造方案

> 目标：把当前「单机 Django-Q + ORM broker」的执行调度，改造成可水平扩展的调度 + 任务分发。
> 分析基准：`execution_control/`、`Tesla/settings.py`、`deploy/docker-compose.yml`

## TL;DR

> ⚠️ **先看第零章：用实测数据判断，你们现在不需要做这个改造。**
> 本文档定位为**技术储备**，供未来真的需要跨机扩容时参考。

**核心结论：当前架构不是"不能扩"，而是"调度器看不见真实容量"。**

`execution_control/dispatcher.py:78` 把并发容量写死成 `settings.Q_CLUSTER["workers"]`（默认 2），**你起再多 worker 容器，调度器仍然只放行 2 个任务** —— 扩容完全无效。

| 阶段 | 动作 | 投入 | 效果 |
|---|---|---|---|
| ① | `capacity` 从配置改读**心跳实测值** + 换 Postgres | 1–2 天 | 扩容立刻生效，掉线自动扣减 |
| ② | scheduler 与 executor **拆成两个角色** | 2–3 天 | executor 想开几个开几个 |
| ③ | DB 租约**选主**，消除 scheduler 单点 | 1–2 天 | 挂了 30 秒自动接管 |
| ④ | Celery + Redis broker + NFS 共享存储 | 2–4 周 | 真正的跨机弹性 |

**做完 ①②③ 只要 4–7 天，并发上限从 2 提到 10–20，且不引入任何新中间件。**
**阶段 ④ 只在"并发持续打满"或"已发生任务丢失事故"时才做。**

> 关键判断：**调度逻辑（DB 里的 FIFO + 资源仲裁）是资产，队列实现（ORM broker）是负债。**
> 改造的全部思路就是——保住资产，替换负债。

## 零、先判断：你到底需不需要这个改造

**上面那份方案是"如果要扩，该怎么扩"。但在动手之前，必须先回答"要不要扩"。**

用你自己的数据算了一遍，结论是：**现在不需要。**

### 0.1 实测证据

从 `db.sqlite3` 的 `execution_control_executiontask` 表（87 条任务记录，81 条有运行时间）用扫描线算法还原历史并发：

| 指标 | 实测值 | 含义 |
|---|---|---|
| **历史最大同时运行任务数** | **1** | 从未同时跑过 2 个 |
| 并发数=1 的累计时长 | 3,954 秒（约 66 分钟） | 全部运行时间里并发数**没有一秒钟超过 1** |
| 队列等待中位数 | 0.2 秒 | 提交即执行 |
| 队列等待 p90 | 1.5 秒 | 基本无排队 |
| `waiting_reason` 非空的记录 | **0 条** | **从未因容量或资源冲突排过队** |

> `waiting_reason` 这一项是最硬的证据。如果容量真的是瓶颈，这个字段会写满"等待资源释放：app-device:3"。它一条都没有。

### 0.2 两个被方案默认掉的前提，你们其实不满足

**前提一：生产库是 MySQL，不是 SQLite。**

`Tesla/settings.py:197`：

```python
if IS_PRODUCTION:
    DATABASES = {"default": {"ENGINE": "django.db.backends.mysql", ...}}
else:
    DATABASES = {"default": {"ENGINE": "django.db.backends.sqlite3", ...}}
```

`deploy/backend.env.example` 里也写着 `DATABASE_ENGINE=mysql`。这意味着：

- **障碍 ⑤（SQLite 整库写锁）在生产环境根本不存在**，`select_for_update()` 本来就是真行锁；
- **阶段 ① 的"换 Postgres"是多余动作** —— 已经是 MySQL 了，不用换；
- `dispatcher.py:140` 那段"`OperationalError: locked` 重试 4 次"是**开发环境 SQLite 的补丁**，生产不触发。

**前提二：部署是单 scheduler 容器，没有副本。**

`deploy/docker-compose.yml` 里 `scheduler` 服务：

```yaml
scheduler:
  command: ["python", "manage.py", "controlled_qcluster"]
  # 没有 deploy.replicas → 只有 1 个实例
```

所以 `capacity = settings.Q_CLUSTER["workers"]` = 2，而真实容量也是 2。**静态容量在当前部署下是正确的，不是 bug。**

> **静态容量只在"多容器"时才出错。** 方案里说它是"第一道墙"，前提是你已经在跑多个 executor —— 而你们没有。这是我在原方案里没说清楚的地方。

### 0.3 所以，内部使用的正确扩容姿势是「改一个环境变量」

单容器部署下，`capacity` 读的就是 `DJANGO_Q_WORKERS`，**扩容不需要任何代码改动**：

```bash
# deploy/backend.env
DJANGO_Q_WORKERS=4     # 从默认 2 提到 4，容量立刻变成 4
```

一行配置，零代码，零架构改动。**这就是内部使用场景下的"水平扩展"。**

注意上限由单机资源决定：UI 自动化要起浏览器实例，很吃 CPU 和内存。一台机器通常能跑 3–6 个 UI 任务，再往上加只会互相拖慢，反而让每个任务都变慢。

### 0.4 那 8 个"等待超 30 秒"的任务是什么

上面统计里有 8 条等待超 30 秒，最长的等了 16.8 小时（9/7 18:17 排队 → 9/8 11:05 开始）。**这不是调度问题**，理由：

- 这 8 条的 `waiting_reason` **全部为空** —— 不是被容量挡住；
- `dispatch_attempts=1`，说明已经派发出去了；
- 16.8 小时那个是**跨夜**的（晚上 18 点提交、第二天上午才开始）。

典型原因是**服务/机器当时没在运行**（开发机晚上关机）。这是可用性问题，不是容量问题，**水平扩展解决不了它**。

### 0.5 什么情况下才回头看这份方案

满足任一条，再来做阶段 ①：

1. **`waiting_reason` 里开始出现"等待资源释放：xxx"** —— 这是容量真的不够的唯一可靠信号（现在 0 条）；
2. 实测并发数**持续**达到 `DJANGO_Q_WORKERS` 上限，且任务开始明显排队；
3. 单机 CPU/内存打满，`DJANGO_Q_WORKERS` 已经加到机器扛不住；
4. 你打算**真的跑多个 scheduler/executor 容器** —— 这才是阶段 ① 的必要前提。

**在满足第 4 条之前，阶段 ①②③④ 全部不需要做。**

### 0.6 内部平台真正该修的是什么

把精力从"扩容"挪到"可用性"上，收益高得多：

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P0** | 任务卡住时**主动告警**（钉钉/企业微信/邮件） | 现在只有主动打开页面才发现任务卡了，`diagnose_tasks()` 诊断完没人知道 |
| **P0** | `aaa.py:5` 硬编码真实 API Key 轮换 + 删文件 | 真实密钥泄露，比任何性能问题都严重 |
| **P0** | `.env` 加入 `.gitignore`（含明文 `DEEPSEEK_API_KEY`） | 后端建 git 仓库前必须先做 |
| **P1** | 前端 `pnpm install` 同步 lockfile | 上一轮清理遗留，不处理下次装依赖会漂 |
| **P1** | scheduler 容器加健康检查 | 挂了能自动重启（已有 `restart: unless-stopped`，补 healthcheck 更稳） |
| **P2** | `DJANGO_Q_WORKERS` 按机器实际能力调到 4 | 一行配置，唯一需要的"扩容" |

### 0.7 一句话

**水平扩展是解决"单机扛不住"的。你们的实测峰值是 1，单机扛得住 6 —— 中间差了 6 倍余量。**

**现在做这套改造，是在花 4–7 天解决一个不存在的问题，同时引入 Postgres 运维、选主机制、更多出错面这些新负债。对内部平台来说，这些复杂度本身就是成本。**

原方案保留，作为**未来的技术储备**：等到 `waiting_reason` 开始出现资源冲突、或者真的要上多容器时，直接照着阶段 ① 做即可。

## 一、现状诊断

### 1.1 当前架构

```
controlled_qcluster（scheduler 容器，单实例）
  ├─ fork 子进程 → manage.py qcluster（消费 ORM broker）
  └─ 主循环 每 10 秒：
       ├─ heartbeat.touch()         上报心跳 + 活跃任务数
       ├─ dispatch_waiting_tasks()  派发
       └─ diagnose_tasks()          诊断（离线 / 停滞）
```

派发逻辑（`dispatcher.py:74` `_reserve_dispatches`）：

1. `select_for_update()` 锁住候选任务行
2. 按 `queued_at, id` 严格 FIFO 排序
3. 逐个做**资源冲突检测**（`resource_keys`，例如 `app-device:3` 表示独占某台设备）
4. 队首资源不足 → **`break`，不允许后来的任务越过它抢空闲槽位**
5. 占用槽位后 `async_task()` 塞进 Django-Q

`Q_CLUSTER`（`settings.py:289`）：

```python
{
    "orm": "default",                        # ← 用数据库当 broker
    "timeout": execution_task_timeout_seconds,
    "retry": execution_task_timeout_seconds + 60,
    "workers": max(1, int(os.getenv("DJANGO_Q_WORKERS", "2"))),
}
```

### 1.2 已经做对的部分（这是改造的最大有利条件）

| 机制 | 位置 | 为什么对扩展有利 |
|---|---|---|
| worker 注册表 + 心跳 | `ExecutionWorker` + `WorkerHeartbeat` | `instance_id = {kind}:{hostname}:{pid}`，天生支持多实例；已有 `capacity` / `active_tasks` / `last_heartbeat_at` 字段 |
| 资源锁存在 DB | `resource_keys` 冲突检测 | 所有实例读同一个库，**天然跨机一致**，不需要额外协调 |
| 完整任务状态机 | `ExecutionTask.status` | 派发/运行/停滞/恢复的语义已定义清楚 |
| 派发超时重试 | `DISPATCH_STALE_SECONDS = 120` | 已有"消息丢失"的兜底 |
| 诊断与恢复 | `diagnose_tasks()` / `recover_task()` | 离线判定、停滞检测、安全重入队 |

**结论：迁移本质是「换掉队列传输层 + 让容量动态化」，不需要重写调度逻辑。**

### 1.3 五个真实障碍（按严重度排序）

#### ① capacity 是静态配置，不是动态容量 —— 最关键

`dispatcher.py:78`：

```python
capacity = max(1, int(settings.Q_CLUSTER.get("workers", 1)))
```

这是**配置常量**。当你把 worker 容器从 1 个扩到 3 个时，每个 scheduler 实例仍然以为总量是 2，于是三边各自放行 2 个 → 实际跑 6 个 → 资源锁被打穿。

**而 `ExecutionWorker.capacity` 字段其实早就存在了**，只是 dispatcher 没有读它。这是一处"设计到位但没接线"的地方。

#### ② ORM broker

数据库当队列，问题有三：

- **多实例轮询同一张表**，实例越多越吵
- **锁竞争**：代码里已经有 `OperationalError: locked` 重试 4 次的补丁（`dispatcher.py:140`），说明 SQLite 下已经在打架
- **没有真正的抢占式消费**：靠 `retry` / `timeout` 做"可见性超时"，语义比 Redis Stream / RabbitMQ 的 ack 粗糙得多

#### ③ 任务体依赖本地文件系统 —— 跨机的硬门槛

`suite/tasks.py:170`：

```python
def run_pytest(path, result_id=0, case_api_count=0, case_ui_count=0):
    runner_log = Path(path) / "logs" / "runner.log"
    ...
    process = subprocess.Popen(command, ...)   # 起 pytest 子进程
```

任务参数里传的是**本地路径**，日志、截图都写本地磁盘。

这意味着：**即使换了 broker，任务落到没有该目录的机器上仍然直接失败。** 跨机分发必须先把共享存储解决掉，这是所有方案的前置条件。

#### ④ scheduler 单点

只有一个 `controlled_qcluster` 容器在跑调度循环。虽然 `restart: unless-stopped` 会拉起，但重启窗口内没人派发；而且它同时承担了"调度"和"跑 qcluster"两个角色，扩不了。

#### ⑤ `select_for_update` 依赖数据库行锁

跨机时依赖 DB 锁语义。Postgres 下没问题，SQLite 下退化成整库写锁，是当前的隐形瓶颈。

## 二、方案总览

四个阶段，**每阶段独立可交付、可回滚**，按投入产出排序：

| 阶段 | 内容 | 解决 | 投入 |
|---|---|---|---|
| **①** | capacity 动态化 + 换 Postgres | 障碍 ①②⑤ | 1–2 天 |
| **②** | scheduler 与 executor 解耦 | 障碍 ④ | 2–3 天 |
| **③** | 加选主（lease）消除单点 | 障碍 ④ | 1–2 天 |
| **④** | 换真 broker + 共享存储 | 障碍 ②③ | 2–4 周 |

**阶段 ①②③ 做完，能撑到 10–20 并发**，且不需要引入新中间件。
**只有并发需求 >20 或确实要跨机时，才需要做阶段 ④。**

## 三、阶段详解

### 阶段 ①：capacity 动态化 + 换 Postgres

**投入 1–2 天｜解决障碍 ①②⑤｜不改架构，只改调度口径**

#### 1.1 问题根因

`execution_control/dispatcher.py:78`：

```python
capacity = max(1, int(settings.Q_CLUSTER.get("workers", 1)))
```

这一行是**整个水平扩展的第一道墙**。它把并发容量钉死在单个进程的环境变量上（`DJANGO_Q_WORKERS`，默认 2）。后果：

- 你起 3 个 worker 容器，每个 4 并发，真实容量是 12；
- 但调度器读到的仍然是 `2`，只放行 2 个任务；
- 另外 10 个槽位永远空转，**扩容器完全没有效果**。

反过来更危险：如果为了"扩容器"把 `DJANGO_Q_WORKERS` 调到 12，那么每个容器里的 `qcluster` 也会各自起 12 个进程，总进程数 = 容器数 × 12，瞬间打爆内存。

**这就是"静态容量"的本质缺陷：它描述的是单进程配置，却被当作全局容量使用。**

#### 1.2 好消息：数据结构已经就绪

`ExecutionWorker` 模型（`execution_control/models.py:63`）**已经有** `capacity` 和 `active_tasks` 两个字段，且 `WorkerHeartbeat.touch(active_tasks=...)` 已经在每 10 秒写一次心跳。**只是调度器从来不读它。**

```python
# 已有字段，未被 dispatcher 使用
capacity = models.PositiveSmallIntegerField("并发容量", default=1)
active_tasks = models.PositiveSmallIntegerField("活动任务", default=0)
last_heartbeat_at = models.DateTimeField("最近心跳", db_index=True)
```

所以阶段 ① 的改动量很小：**把"读配置"换成"读在线 worker 的 capacity 之和"。**

#### 1.3 具体改法

在 `dispatcher.py` 顶部加一个容量计算函数（需补 `Sum` 与 `ExecutionWorker` 的导入）：

```python
from django.db.models import F, Q, Sum          # 原为 F, Q，补 Sum
from .models import ExecutionTask, ExecutionWorker   # 原仅 ExecutionTask

WORKER_FRESH_SECONDS = 60  # 心跳超过这个时间视为掉线，其容量不计入

def _online_capacity():
    """在线执行器的容量之和。心跳过期的实例不参与计算，避免容量虚高。"""
    fresh_after = timezone.now() - timedelta(seconds=WORKER_FRESH_SECONDS)
    total = ExecutionWorker.objects.filter(
        kind=ExecutionWorker.Kind.SCHEDULER,
        status=ExecutionWorker.Status.ONLINE,
        last_heartbeat_at__gte=fresh_after,
    ).aggregate(total=Sum("capacity"))["total"]
    # 全下线时退回配置值，保证系统不会因为"无人认领"而完全停止派发
    return max(1, int(total or settings.Q_CLUSTER.get("workers", 1)))
```

然后把第 78 行替换为：

```python
capacity = _online_capacity()
```

同时 `ExecutionWorker` 的 `capacity` 必须在心跳里写成**真实的 qcluster 并发数**（即 `DJANGO_Q_WORKERS`），而不是默认的 1。检查 `WorkerHeartbeat.__init__` 与 `touch()`，确保 `capacity` 被显式传入。

#### 1.4 为什么这样就能扩容器

改完之后语义变成：

| 场景 | 改前放行数 | 改后放行数 |
|---|---|---|
| 1 容器 × 2 并发 | 2 | 2 |
| 3 容器 × 4 并发 | 2（扩容无效） | 12 |
| 1 个 worker 挂掉（心跳停） | 仍按 2 放行，任务堆积 | 自动扣减，容量=实际存活 |

**容量从此是"实测值"而非"配置值"，扩容器立刻生效，掉线自动收敛。**

#### 1.5 换 Postgres（同日可做）

SQLite 下 `select_for_update()` 退化为整库写锁，`dispatcher.py:140` 那段"遇到 `OperationalError: locked` 重试 4 次"的补丁就是为它打的。换 Postgres 后：

- `select_for_update()` 变成真正的行锁，多个调度器可以并发预留互不干扰；
- 那段重试逻辑可以删掉（保留也无害，只是永不触发）；
- `retry=timeout+60` 之外不再需要额外的锁等待容忍。

迁移注意：

1. `dj_db` 相关的 ORM broker 表（`django_q_ormq`、`django_q_task`）由 Django-Q 自建，`migrate` 时自动生成；
2. 72 张表中若有 `JSONField` 的 SQLite 特殊写法，需检查（Django 4.2 已统一，一般无需改）；
3. **先全量 dump 再迁**，SQLite 没有真正的事务隔离保证，边写边迁有丢数据风险。

#### 1.6 阶段 ① 验收标准

- 起 2 个 worker 进程，各自 `DJANGO_Q_WORKERS=4`，观察 `ExecutionTask` 的 `QUEUED → RUNNING` 转化数应能达到 8；
- 杀掉其中一个 worker 进程，60 秒后放行上限自动降为 4；
- 并发提交 10 个任务，无 `OperationalError: locked` 日志。

### 阶段 ②：scheduler 与 executor 解耦

**投入 2–3 天｜解决障碍 ④｜让执行器可以独立扩缩**

#### 2.1 当前耦合点

`controlled_qcluster.py` 现在是"一个进程同时干三件事"：

```python
# 伪代码还原
proc = subprocess.Popen([sys.executable, manage.py, "qcluster"])   # ① 执行器
while True:
    heartbeat.touch(active_tasks=active)      # ② 心跳
    dispatch_waiting_tasks()                  # ③ 调度
    diagnose_tasks()                          # ④ 诊断
    time.sleep(10)
```

问题在于：**执行器和调度器是同一个进程组。** 想加执行器，就必须连带复制一个调度循环；而两个调度循环同时跑，就会双份派发（阶段 ③ 才解决）。

#### 2.2 目标形态

拆成两类角色，用**同一个镜像、不同的启动命令**区分：

| 角色 | 启动命令 | 职责 | 可否多副本 |
|---|---|---|---|
| **scheduler** | `python manage.py controlled_qcluster --role=scheduler` | 只做 heartbeat + dispatch + diagnose | 阶段③前只能 1 个 |
| **executor** | `python manage.py qcluster` | 只消费队列、跑 pytest | ✅ 想开几个开几个 |

关键点：**executor 用 Django-Q 原生 `qcluster` 命令，不再包一层。**

#### 2.3 改法

把 `controlled_qcluster.py` 拆成两个命令：

```python
# execution_control/management/commands/controlled_qcluster.py
class Command(BaseCommand):
    def add_arguments(self, parser):
        parser.add_argument("--role", choices=["all", "scheduler"], default="all")
        parser.add_argument("--executors", type=int, default=1)

    def handle(self, *args, **options):
        role = options["role"]
        children = []
        if role == "all":
            # 兼容旧部署：单机模式下仍然一把起，行为不变
            children.append(self._spawn_qcluster())
        self._scheduler_loop()      # 只跑心跳 + 派发 + 诊断
```

`_spawn_qcluster()` 就是现在那段 `subprocess.Popen([... "qcluster"])`，原样保留。区别是**当 `--role=scheduler` 时它不再被调用**。

新增一个纯执行器入口（其实就是原生命令，不用写代码）：

```bash
python manage.py qcluster
```

#### 2.4 部署形态

docker-compose 示意：

```yaml
services:
  scheduler:
    command: python manage.py controlled_qcluster --role=scheduler
    deploy: { replicas: 1 }          # 阶段③后改成 >1

  executor:
    command: python manage.py qcluster
    deploy: { replicas: 3 }          # 想扩就改这个数
    environment:
      DJANGO_Q_WORKERS: "4"          # 单容器 4 并发 → 总容量 12
```

注意 `DJANGO_Q_WORKERS` 只对 executor 有意义；scheduler 不再需要它（因为容量已经改从 `ExecutionWorker.capacity` 读）。

#### 2.5 一个必须处理的细节：executor 也要心跳

现在只有 `controlled_qcluster` 在写心跳。拆开之后，**纯 executor 进程也必须注册并心跳**，否则阶段 ① 的 `_online_capacity()` 算不到它们，容量永远是 0（会退回配置默认值，等于白改）。

做法：给 `qcluster` 加一个 `--run-once` 之外的钩子比较麻烦，更简单的是写一个薄包装命令：

```python
# execution_control/management/commands/qworker.py
class Command(BaseCommand):
    """启动原生 qcluster，同时在父进程里维持心跳。"""
    def handle(self, *args, **options):
        beat = WorkerHeartbeat(kind=ExecutionWorker.Kind.SCHEDULER,
                               capacity=int(settings.Q_CLUSTER["workers"]))
        proc = subprocess.Popen([sys.executable, BASE_DIR / "manage.py", "qcluster"])
        try:
            while proc.poll() is None:
                beat.touch(active_tasks=_count_running())
                time.sleep(10)
        finally:
            beat.mark_offline()
            proc.terminate()
```

这样 executor 容器 = `python manage.py qworker`，既能跑原生 qcluster，又能被调度器"看见"。**这是阶段 ① 真正生效的前提，两个阶段要一起上。**

#### 2.6 阶段 ② 验收标准

- `--role=scheduler` 进程内 `ps` 看不到 qcluster 子进程；
- executor 容器扩到 3 个，`ExecutionWorker` 表出现 3 条 online 记录，`capacity` 各为 4；
- 调度器放行上限 = 12（验证阶段 ① 的动态容量确实读到了多个 executor）；
- 停掉全部 executor，任务保持 `QUEUED` 且 `waiting_reason` 显示等待，不报错。

### 阶段 ③：选主（lease）消除单点

**投入 1–2 天｜解决障碍 ④｜让 scheduler 也能挂**

#### 3.1 为什么必须选主

阶段 ② 之后 scheduler 是**唯一副本**。它挂了 → 心跳停、派发停，队列里的任务全部卡死（执行器还在跑已派发的，但新任务不会再有）。这是典型的单点。

但不能简单地把 scheduler 也开 3 副本：`_reserve_dispatches()` 里的"预留 + 严格 FIFO"逻辑要求**全局只有一个人在决策**，两个调度器同时跑会各自读到 `dispatched_at__isnull=True` 的同一批任务，**双份派发**，同一台设备被两个任务占用。

所以需要**主从**：多副本待命，只有 leader 真正派发。

#### 3.2 用数据库租约实现（不引入 Redis/etcd）

新增一张极小的表：

```python
class SchedulerLease(models.Model):
    """调度器主租约。同一时刻只有一个实例能拿到未过期的租约。"""
    name = models.CharField(max_length=64, unique=True)   # 固定 "dispatcher"
    owner = models.CharField(max_length=160)              # instance_id
    lease_expires_at = models.DateTimeField(db_index=True)
```

抢主逻辑（利用已有的 Postgres 行锁，**无需任何新中间件**）：

```python
def acquire_lease(instance_id, ttl=30):
    """尝试成为主调度器。返回 True 表示本进程获得派发权。"""
    now = timezone.now()
    with transaction.atomic():
        lease = SchedulerLease.objects.select_for_update().filter(name="dispatcher").first()
        if lease is None:
            SchedulerLease.objects.create(
                name="dispatcher", owner=instance_id,
                lease_expires_at=now + timedelta(seconds=ttl))
            return True
        if lease.owner == instance_id or lease.lease_expires_at < now:
            # 自己续约，或前任已过期（挂了）→ 接管
            lease.owner = instance_id
            lease.lease_expires_at = now + timedelta(seconds=ttl)
            lease.save(update_fields=["owner", "lease_expires_at"])
            return True
        return False   # 别人持有有效租约，本进程保持待命
```

调度循环改成：

```python
while True:
    if acquire_lease(instance_id):
        dispatch_waiting_tasks()
        diagnose_tasks()
    else:
        self._standby_log()      # 每 10s 尝试一次抢主
    time.sleep(10)
```

关键设计点：

- **TTL=30s，循环 10s** → leader 每轮续约，留 3 次容错；进程被杀后最长 30 秒接管，任务不会卡太久。
- **`select_for_update()` 保证原子性**：两个副本同时抢，DB 行锁让它们串行，后到的读到未过期租约就退出。
- **`owner == instance_id` 分支**是续约，不是抢主，避免自己把自己锁掉。
- 心跳表 `ExecutionWorker` 可以继续由**所有副本**写（便于观测有几个待命实例），只有**派发权**是排他的。

#### 3.3 为什么不用 Redis 分布式锁

可以用，但没必要：

- 引入 Redis 只为了一把锁，运维成本不划算；
- Postgres 行锁已经够快（这条 SQL 每 10 秒执行一次，压力可忽略）；
- 租约状态落库可查，出问题时 `SELECT * FROM scheduler_lease` 一眼看清谁在主。

**等阶段 ④ 真的引入 Redis 了，再把租约迁过去也不迟。**

#### 3.4 阶段 ③ 验收标准

- 起 3 个 scheduler 副本，日志中只有 1 个持续打印"派发 N 个任务"，另 2 个打印"待命"；
- `kill -9` 当前 leader，**30 秒内**另一个副本接管并继续派发；
- 接管过程中，无任何任务被重复派发（校验 `ExecutionTask.dispatch_attempts` 未异常增长、无重复 `resource_keys` 冲突日志）。

### 阶段 ④：换真 broker + 共享存储

**投入 2–4 周｜解决障碍 ②③｜只有确实要跨机时才做**

阶段 ①②③ 是"在现有架构上把容量释放出来"，阶段 ④ 才是"换架构"。**先做完前三阶段，用真实并发数据判断要不要走这一步。**

#### 4.1 障碍 ② 的本质：ORM broker 不是队列

现在 `Q_CLUSTER["orm"] = "default"`，队列就是 `django_q_ormq` 表。它的问题不是性能，而是**语义**：

| 能力 | ORM broker | 真 broker（Redis/RabbitMQ） |
|---|---|---|
| 消息确认（ack） | ❌ 取走即删，进程崩溃任务消失 | ✅ ack 后删，崩溃自动重投 |
| 可见性超时 | ❌ 靠 `retry` 时间猜 | ✅ 原生 unacked 回队 |
| 多消费者竞争 | 靠 DB 行锁抢 | ✅ 原生竞争消费 |
| 背压/长度限制 | ❌ 无 | ✅ maxlen / 队列上限 |
| 跨机房 | ❌ DB 是中心 | ✅ 可桥接 |

**最关键的是 ack。** 现在 executor 进程被 `kill -9`，那个任务的消息已经从 `ormq` 表里删掉了，任务永久消失——只能靠 `diagnose_tasks()` 事后扫描 `ExecutionTask` 表发现"卡在 RUNNING 但没人跑"来补救。这是当前最脆弱的一环。

#### 4.2 方案选型

三条路线，按"改动量 vs 收益"排：

| 方案 | 改动 | 收益 | 适合 |
|---|---|---|---|
| **A. Celery + Redis** | 中（换装饰器、换派发调用） | 完整 ack/重试/路由/优先级 | **推荐** |
| **B. Django-Q2 + Redis broker** | 小（只改 `Q_CLUSTER`） | 拿到 ack 与竞争消费，但**派发逻辑仍在 DB** | 想快速止血 |
| **C. RabbitMQ + Celery** | 大 | 最强可靠性、延迟队列 | 有专职运维 |

**推荐 A（Celery + Redis）**，理由：

1. `dispatcher.py` 的 `_enqueue_task()` 已经是唯一派发出口，换成 `celery_app.send_task()` 改动集中；
2. `suite/tasks.py` 的 `run_pytest` 只需加 `@shared_task` 装饰器，函数签名不用动；
3. Celery 的 `acks_late=True` + `task_reject_on_worker_lost=True` 直接解决障碍 ②；
4. Redis 同时可以当缓存和分布式锁，一份中间件多用。

**不建议一上来就 RabbitMQ**：它的可靠性优势要在"不能丢消息"的强约束下才体现，而本场景丢一个任务只需重跑，收益不匹配运维成本。

#### 4.3 迁移要点（别踩的坑）

1. **`acks_late` 必须配幂等**。开启后任务可能被执行两次，`run_pytest` 里"创建 result_id 记录"那步要么加唯一约束，要么用 `get_or_create`。
2. **`visibility_timeout` 要大于最长任务时长**。`execution_task_timeout_seconds + 300` 是现在的口径，Redis broker 的 `visibility_timeout` 必须设得比它更大，否则长任务会被重复投递——这正是现在注释里"retry 必须大于 timeout"的同一个坑。
3. **严格 FIFO 要重新实现**。现在是"队首资源不足就 `break`"保证不插队。Redis 是竞争消费，天然无序。保留 FIFO 的做法：**调度权仍在 DB（阶段③的 leader），Celery 只当执行通道** —— 即 leader 按 FIFO 挑出任务后逐个 `send_task`。这样 FIFO 语义完全保留在已有的 `_reserve_dispatches()` 里，**不用重写**。
4. **`resource_keys` 的独占语义不变**，仍然由 DB 的 `select_for_update` 保证。Celery 不参与资源仲裁。

> 第 3、4 点很重要：**不要把调度逻辑搬进 Celery。** Celery 只替换"从调度器到执行器的运输管道"，`ExecutionTask` 表仍是唯一事实源。这样即使 Celery 出问题，任务状态依然可查可恢复。

#### 4.4 障碍 ③：任务体依赖本地文件系统

这是**比 broker 更难的一关**，也是"能不能真正跨机"的分水岭。

`suite/tasks.py:170`：

```python
def run_pytest(path, result_id=0, case_api_count=0, case_ui_count=0):
    # 在 Path(path)/logs/runner.log 写日志，subprocess 起 pytest
```

它拿到的是**本地路径**。当前架构下没问题，因为调度器和执行器在同一台机器、同一个挂载点。一旦 executor 分布在多台机器上：

- 派发出去的 `path` 在目标机器上不存在 → 任务必失败；
- 就算路径存在，`logs/runner.log` 写在本地，日志回收接口读不到。

**三种解法：**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **NFS / 共享挂载** | 所有 executor 挂同一个 NFS，`path` 语义不变 | 代码**零改动** | NFS 性能差、单点、小文件多时很慢 |
| **对象存储 + 本地缓存** | 任务开始时从 S3/MinIO 拉取到本地临时目录，结束回传 | 真正无状态、可弹性 | 需改造任务前后置钩子 |
| **任务包直传** | 派发时把用例包打成 tar 传给 executor | 无共享依赖 | 大包传输慢、重复传输 |

**落地建议：**

- **先上 NFS**（半天工作量，零代码改动）验证"跨机派发"这条路走得通；
- 如果用例包不大（<10MB）、且日志回收能接受延迟，**NFS 就够了，不必做对象存储**；
- 只有当 executor 需要**按需弹性扩缩**（比如上 K8s）时，才值得做对象存储 + 本地缓存 —— 因为 NFS 无法跟随 Pod 生命周期。

#### 4.5 阶段 ④ 的触发条件（别提前做）

**满足以下任一条，才动手：**

1. 阶段 ①②③ 上线后，实测并发上限（10–20）**持续被打满**，且 `waiting_reason` 长期显示等待资源；
2. 单机 CPU/内存已成为瓶颈，必须跨机；
3. 出现"executor 崩溃导致任务丢失"的**真实生产事故**（这是 ack 缺失的直接后果，也是最强的做阶段④的理由）。

**不满足就别做。** 换 broker 是 2–4 周投入，而阶段 ①②③ 只花 4–7 天就能拿到 5–10 倍容量提升。先把便宜的收益吃掉。

## 四、风险与回滚

### 4.1 各阶段风险矩阵

| 阶段 | 主要风险 | 严重度 | 回滚方式 |
|---|---|---|---|
| ① capacity 动态化 | 心跳口径写错导致容量虚高 → 超量派发 | **高** | 恢复第 78 行读配置（一行改动） |
| ① 换 Postgres | 数据迁移丢数据 | **高** | 迁移前全量 dump，SQLite 文件保留不删 |
| ② 拆 scheduler/executor | executor 未注册心跳 → 容量算成 0 → 完全停止派发 | **中** | `--role=all` 回退到单机模式 |
| ③ 选主 | TTL 过短 → 双 leader 抖动 | **中** | TTL 调大或临时降到 1 副本 |
| ④ 换 broker | `acks_late` 重复执行、`visibility_timeout` 配错 | **高** | 保留 `dispatcher` 开关，切回 ORM broker |

### 4.2 三个必须守住的红线

**红线 1：任何阶段都不能破坏"严格 FIFO + 资源独占"。**
这是防"同一台设备被两个任务同时占用"的唯一保障。改容量计算、拆进程、加选主，都只动"谁有权派发"和"能派发几个"，**不动"按什么顺序派发"**。`_reserve_dispatches()` 里那段 `break` 逻辑，除非重写测试，否则一行都不要改。

**红线 2：`ExecutionTask` 表始终是唯一事实源。**
无论后面换成 Celery 还是别的，任务状态、资源占用、等待原因都必须落在这张表。**不要依赖 broker 的队列内容判断"还有什么在跑"** —— broker 里的消息会丢、会重复、会过期，DB 记录不会。

**红线 3：`retry` / `visibility_timeout` 必须大于最长任务时长。**
settings 里那句注释是血泪经验：

> `retry 必须大于 timeout，否则长任务会被队列重复投递，造成同一设备被重复占用。`

换成 Celery 后这条约束**依然存在**，只是换了参数名（`visibility_timeout`）。**改 broker 时最容易漏掉的就是它。**

### 4.3 灰度与观测

每阶段上线前，至少要有这几条可观测数据，否则无法判断是否真的变好了：

- **容量口径**：`_online_capacity()` 的计算结果 vs `ExecutionWorker` 表实际记录（对不上就是口径 bug）；
- **放行转化率**：`QUEUED → RUNNING` 的平均等待时长（这是容量是否充足的直接指标）；
- **重复派发**：`dispatch_attempts > 1` 的任务数（阶段③选主是否正确）；
- **任务丢失**：`status=RUNNING` 但 `started_at` 超过 `timeout + 300` 的记录数（阶段④ ack 是否必要）。

### 4.4 建议的落地顺序

```text
第 1 周   阶段 ①   （动态容量 + Postgres）      ← 立竿见影，风险最低
第 2 周   阶段 ②   （拆 scheduler/executor）    ← 依赖 ①，必须一起验证
第 2–3 周 阶段 ③   （选主）                    ← 消除单点
—— 观察 2–4 周，收集上面 4 项指标 ——
满足触发条件 → 阶段 ④（broker + NFS）
不满足       → 停在此处，收益已经吃满
```

## 五、结论

### 5.1 一句话结论

**当前的 Django-Q 架构不是"不能水平扩展"，而是"调度器看不见真实容量"。** 阶段 ① 一行改动（`capacity` 从配置改读心跳）就能解除扩容的第一道墙，配合 ②③ 共 4–7 天投入，可把并发上限从 2 提到 10–20，且**不引入任何新中间件**。

### 5.2 该做什么

| 优先级 | 动作 | 理由 |
|---|---|---|
| **P0** | 阶段 ①：`_online_capacity()` + 换 Postgres | 投入 1–2 天，直接决定"扩容器有没有用" |
| **P0** | 阶段 ② 的 `qworker` 心跳包装 | 不做则阶段 ① 完全失效 |
| **P1** | 阶段 ③：DB 租约选主 | 消除 scheduler 单点，30 秒自动接管 |
| **P2** | 阶段 ④：Celery + Redis | 仅当出现任务丢失事故或并发持续打满 |
| **P2** | 阶段 ④：NFS 共享存储 | 跨机的前置条件，优先 NFS 而非对象存储 |

### 5.3 不该做什么

- ❌ **不要为了"扩容器"调大 `DJANGO_Q_WORKERS`** —— 那是单进程配置，容器数 × 它 = 真实进程数，会直接打爆内存；
- ❌ **不要把调度逻辑搬进 Celery** —— FIFO 和资源仲裁留在 DB，Celery 只当运输管道；
- ❌ **不要在没有真实并发压力时提前做阶段 ④** —— 2–4 周投入换来的收益，前三阶段 4–7 天就能拿到大部分；
- ❌ **不要删掉 `retry > timeout` 的约束** —— 换 broker 时它只是换了参数名。

### 5.4 与代码价值评估的呼应

`docs/代码价值评估报告.html` 里把调度层归为"真自研"，这份方案是对该结论的延伸：

- **值得保留的**：`_reserve_dispatches()` 的严格 FIFO + `resource_keys` 资源仲裁，是这套平台的核心竞争力，**换任何 broker 都不用重写**；
- **属于技术债的**：静态 `capacity`、ORM broker、任务体依赖本地路径 —— 这三项是"能用但不可扩"的根源，也正是本方案阶段 ①④ 针对的目标。

**调度逻辑本身是资产，队列实现是负债。** 方案的全部思路就是：**保住资产（DB 里的调度决策），替换负债（运输管道）。**
