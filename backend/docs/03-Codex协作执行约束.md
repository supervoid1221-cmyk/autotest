# Codex 协作执行约束

> 本文档用于约束 Codex 在本项目中的沟通、代码修改、验证、数据处理和发布行为。除非用户在当前任务中给出新的明确指令，否则 Codex 必须严格遵守本文档。

## 1. 指令优先级

1. 以用户当前最新、最明确的指令为最高执行依据。
2. 当前指令与历史要求冲突时，以当前指令为准，并在执行前说明影响。
3. 不擅自扩大任务范围，不顺带修改用户未要求的模块。
4. 需求存在关键歧义，且不同理解会产生明显不同结果时，先说明问题并询问，不自行猜测。

## 2. 执行前沟通

1. 每次准备修改代码前，必须先用简洁语言说明：
   - 问题原因或当前判断；
   - 准备采用的解决方案；
   - 预计涉及的修改范围。
2. 不允许在没有说明原因或方案的情况下直接开始修改代码。
3. 如果用户只要求方案、评估、原型图或原因分析，不得直接修改代码。
4. 用户明确要求“按照方案修改代码”或同等含义后，才实施对应改造。

## 3. 代码修改范围

1. 默认只修改本地代码。
2. 未经明确指令，不得：
   - 推送 Git 仓库；
   - 创建或合并远程分支；
   - 发布到生产环境；
   - 修改生产服务器；
   - 同步本地数据到生产环境。
3. 修改时保留用户已有代码和无关改动，不回滚、不覆盖无关内容。
4. 只处理当前需求涉及的前端、后端、数据库或文档范围。
5. 当前平台数据量较少，后续功能改造默认不需要兼容历史数据；如果可能造成重要数据丢失，仍需提前说明。

## 4. 验证与测试

1. 修改代码后，未经用户明确指令，不得主动执行任何验证，包括但不限于：
   - 前端构建；
   - 后端测试；
   - 单元测试或集成测试；
   - lint、类型检查；
   - 启动或重启服务；
   - 调用接口；
   - 操作浏览器验证页面；
   - 执行数据库查询验证结果。
2. 完成修改后，只说明已修改的内容和涉及文件，不得声称“已经验证通过”。
3. 只有用户明确提出“验证、测试、检查运行结果、构建确认”等要求时，才执行相应验证。
4. 用户指定验证范围时，不扩大验证范围。

## 5. Git 与仓库

1. 默认不执行 `git add`、`git commit`、`git push`、合并、变基或打标签。
2. 只有用户明确要求提交或推送时才操作。
3. 推送前说明目标仓库、分支及提交范围。
4. 不把密码、私钥、Token、数据库凭据或生产环境配置提交到仓库。

## 6. 生产发布

1. 只有用户明确要求“发布生产”或给出同等授权时，才允许操作生产服务器。
2. 发布前说明：
   - 发布代码范围；
   - 数据库变更；
   - 服务重启范围；
   - 可能影响。
3. 发布生产时，不同步本地业务数据。
4. 数据库只同步表结构、字段和必要迁移；除非用户明确要求迁移数据。
5. 不开放额外公网端口、不修改防火墙或数据库公网访问策略，除非用户明确要求。
6. 不在回复、日志或命令输出中主动暴露服务器密码、数据库密码、私钥和 Token。

## 7. 数据库与数据安全

1. 删除、清空、覆盖、迁移数据前，必须确认目标和范围。
2. 未经明确指令，不执行数据删除、批量更新、表结构破坏性操作或生产数据迁移。
3. 用户要求仅调整表和字段时，不携带本地表数据。
4. 数据库迁移文件应与实际模型变更保持一致。
5. 涉及凭据时仅说明获取位置或配置方式，不在文档中写入真实密码。

## 8. 前端与 UI 修改

1. 用户提供原型图并要求按图修改时，应以原型图的布局、比例、间距、对齐、颜色和交互为准。
2. 用户要求“1:1”或“严格按照原型图”时，不自行增加额外视觉元素或改变信息层级。
3. 修改后如果用户未要求验证，不主动打开页面检查效果。
4. 同行的 `n-form-item` 必须保留单行网格结构，保证标签、输入框和下拉框处于统一水平线。
5. UI 优化不得破坏原有业务逻辑、权限控制、数据保存和交互行为。
6. 用户只要求样式调整时，不修改接口、数据结构或业务逻辑。

## 9. 前后端与权限逻辑

1. 涉及项目数据的功能，应遵循项目权限过滤；系统管理员默认可查看全部项目数据。
2. 列表筛选、分页和权限有关时，优先保证服务端筛选口径正确，避免仅前端过滤造成分页错误。
3. 修改接口字段或数据库字段时，同步处理必要的前端、后端和迁移定义，但不额外兼容历史数据，除非用户要求。
4. 不通过前端隐藏代替后端权限校验。

## 10. 文档与交付说明

1. 文档默认放在项目 `docs` 目录，使用清晰、可维护的 Markdown 格式。
2. 完成代码修改后，简要说明：
   - 修改结果；
   - 主要涉及文件；
   - 未执行的验证（如适用）。
3. 不夸大结果，不把“已修改”描述成“已验证通过”。
4. 如果任务被阻塞，应说明具体原因和需要用户提供的信息。

## 11. 默认工作流程

1. 阅读用户需求并确认范围。
2. 先说明原因、解决方案和修改范围。
3. 只修改本地、当前需求相关的代码或文档。
4. 未经指令，不执行测试、构建、运行和页面验证。
5. 未经指令，不提交仓库、不发布生产、不迁移数据。
6. 向用户说明实际完成内容和未执行事项。

## 12. 当前明确约束摘要

- 修改代码前先说明原因或方案。
- 没有用户指令，修改后不自行验证。
- 默认只修改本地，不更新仓库，不同步生产。
- 发布生产时不携带本地数据，只同步表结构和字段；数据迁移必须单独授权。
- 后续改造默认不考虑历史数据兼容，但破坏性操作仍需提前说明。
- 同行 `n-form-item` 保持单行网格和水平对齐。
- 原型图要求严格还原时，不自行改变布局和交互。
