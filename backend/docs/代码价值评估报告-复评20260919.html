P1核实第三方签名密钥的合规风险

fullstack_framework/commons/helix_signature.py:21 里有一个硬编码值 _WEB_DEFAULT_SECRET = "9697761f6c77"，注释说明它来自 「MXN WEB 0.2.277 初始化签名 Store 时使用的默认值」、可从浏览器抓包复算。

性质说明：这不是平台自身的密钥泄漏，而是一段为兼容某个第三方 Web 应用而逆向出来的前端签名密钥。 两个风险：① 技术上——对方一旦轮换该值，抓包导入功能会静默失效； ② 合规上——逆向并使用第三方应用的私有签名机制，在对外商业化时可能构成争议点。建议在做技术输出或融资前先明确这一条的法律边界。

07结论

技术价值真实且在提升，资产成熟度仍是短板——但短板的位置变了。

建议按以下顺序推进：

  1. 立刻做（半天内）：给在用后端 git init 并提交全量；给前端本地仓库加 remote 并推送； 删除 .codex_tmp/ 与 autotest/backend/aaa.py。 这一步把「本周的多租户改造只存在一块磁盘上」的风险直接消掉，成本几乎为零。
  2. 本周做：决定 autotest/ 与在用目录的关系，消除三副本并存。 当前状态是最坏的：既不是「没版本控制」（那至少只有一份），也不是「有版本控制」（那三份应该一致）。
  3. 本月做：类型检查接进构建（先能报错，再收敛 1,279 处 any）；给 19 个超长单行文件加格式化规则； 把 16 处静默 except: pass 补上日志。
  4. 把 smart_locator 当成核心资产单独对待：补测试、补文档、把定位策略做成可配置项。 这是全项目唯一具备差异化壁垒的部分——如果未来要做技术输出或融资，这是唯一需要重点讲的东西， 其余（套件编排、接口测试、性能测试）都属红海。
  5. 拆长函数前先补测试：suite/models.py 的 run() 与 smart_locator/engine.py 是全平台最核心也最难改的地方，没有测试覆盖时不要动。
