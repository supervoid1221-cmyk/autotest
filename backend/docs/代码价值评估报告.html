第一层 · 真自研 护城河在这里
这些模块解决了非平凡的技术问题，且有非平凡的算法或状态机
  • UI 智能定位引擎 case_ui/smart_locator/engine.py（1,219 行）— 全项目最有价值的单个文件。实现了：编辑距离模糊匹配（_edit_distance / _fuzzy_score）、DOM 作用域隔离（_active_scope / wait_for_active_scope）、跨 UI 框架弹窗识别（选择器同时兼容 dialog / ant-modal / el-dialog / v-dialog / drawer）、表格行定位（按列名匹配行 _find_row_scope）、滚动区域搜索（_scroll_search_regions）、UI 过渡状态等待（start_ui_transition_watch）。11 种回退策略加权评分 + 歧义保护。
  • 定位自愈能力 smart_locator/fingerprints.py + engine.py:849/908 — 定位成功的元素会生成可复用表达式并持久化指纹，后续失败时先尝试指纹回退。这是商业 UI 自动化工具的收费卖点，这里自己做出来了。
  • 断言与变量引擎 fullstack_framework/commons/api_executor.py（620 行）— 自建 ${} / {{}} 双语法变量解析、15+ 提取器白名单、轮询与失败重试状态机。不是包 requests。
  • 任务调度与故障恢复 execution_control/dispatcher.py — 基于 select_for_update 的 FIFO 资源预留、资源冲突检测、Worker 心跳存活判定、离线任务自动恢复（diagnose_tasks / recover_task）。有真实的状态机。
  • 动态函数安全沙箱 project/function_sandbox.py — AST 白名单 + resource 限额，且独立跑在 dynamic-function-runtime 容器的 unix socket 上。安全设计有诚意。
  • 密钥轮换 Tesla/encryption.py — 用 MultiFernet 支持密钥轮换，不是简单 AES 一把梭。
第二层 · 半自研 在开源内核上做了实质改造
底层能力来自第三方，但上层有大量自研改造，改造部分是有价值的
  • Playwright 执行器 case_ui/playwright_executor.py（1,027 行）— 引擎是 Playwright，但定位回退、自愈锚点、OCR 兜底是自己加的。
  • 统一执行编排 suite/models.py:344 的 Suite.run() — 支持 API / UI / Playwright / App 四类步骤交错执行、变量优先级（project < environment_token < template）、失败重试、continue_on_failure、DDT 数据驱动、条件分支、cron/webhook 触发。
  • 性能测试 performance/runner.py（604 行）— 压测内核是 k6 二进制，但 k6 脚本由自研代码生成（build_script），且自研了 5 秒桶聚合、p50–p99 百分位计算、实时增量消费。
  • Appium 客户端 case_app/appium_client.py — 手写 Appium REST 协议调用，非官方 SDK。
  • 监控告警状态机 monitor/services.py — 数据源是 Prometheus HTTP API，但 warning / critical / recovered 状态流转与去重是自己写的。
  • 环境认证 project/models.py:247 — 自动登录 + Token 缓存 + 跨进程文件锁（runtime_auth_locks/），解决了并发执行时重复登录的真实痛点。
第三层 · 胶水与外包 价值主要在于整合，不在于技术
这部分是「把它们接起来」的工程劳动，可替代性高
  • fullstack_framework/commons/session.py — BeifanSession(requests.Session)，本质是包了一层 requests。
  • 套件执行依赖 pytest 子进程 + Django-Q2 队列，没有自研执行器。
  • 压测能力完全依赖 k6 二进制；监控数据完全依赖 Prometheus / node_exporter。
  • ai_assistant 仅 96 行 — 真接了 DeepSeek API，但是薄转发：无平台上下文注入、无工具调用。属于「能聊天」，不是「AI 驱动测试」。前端 components/Ai 里的 AI 洞察已接入执行报告，这块是活的。
  • 前端 src/views/comp form list result setting 共 35 个页面是 UI 模板自带的 demo，未改造。

04折价项与风险

这些是必须在估值里扣掉的部分。按严重程度排序

严重项目没有任何版本控制

后端和前端都不是 git 仓库，磁盘上不存在 .git。这意味着：无法追溯任何一行代码是谁、何时、为何改的；无法回滚误删；无法多人协作；无法做分支发布；也无法向任何第三方证明开发过程。对一份要评估或交易的代码资产而言，这是最重的一条折价项——它让「交付物」和「一堆文件」的区别消失了。

严重密钥明文存在于磁盘

aaa.py:5 硬编码了一个真实格式的 API Key（sk-6d42cf…）；.env:2 有明文 DEEPSEEK_API_KEY。虽然 .gitignore 已排除 .env，但该文件仍在磁盘上，且 aaa.py 是未被忽略的普通源码文件。建议立即轮换这两个 Key 并删除 aaa.py。

中约 29% 前端页面是模板遗留

122 个 .vue 里，35 个是 UI 模板自带的 demo（comp/* 9 个、setting/* 7 个、form/* 6 个、result/* 3 个等），另有若干孤儿页（case_api/my_sfc.vue、project/project_variable.vue 零引用）。加上已确认的死代码：api/schema.d.ts（2,295 行，零 import）、components/Http、components/CountTo、plugins/customComponents.ts + globalMethods.ts（main.ts:23,29 已被注释掉）——合计约 7–8 千行是死代码。

中类型检查与 Lint 形同虚设

构建脚本只有 vite build，没有 vue-tsc 做类型校验，所以类型错误不会阻断构建；tsconfig 虽然 strict: true，但 noImplicitAny: false、strictFunctionTypes: false；ESLint 配置里 no-explicit-any 关闭、ban-ts-comment 关闭。结果是全项目 109 处 any（scenario_edit.vue 一个文件就 188 处含 as any）。

中超大文件与压缩代码

前端 9 个文件超过 800 行（最大 ui_case_edit.vue 2,904 行）；后端 3 个超过 1,000 行（engine.py 1,219 / playwright_executor.py 1,027 / suite/models.py 1,005），其中 suite/models.py:344 的 run() 单函数 447 行。更麻烦的是前端有 20 个文件存在超过 1,500 字符的单行（最长 9,007 字符），源码被压成一整行，Code Review 和后续维护成本很高。

低其他技术债

① 生产 dist 里残留 69 处 console.log——.env 里的 VITE_DROP_CONSOLE=true 没有接进 vite.config.ts；② 冗余依赖零引用：json-editor-vue、vue-draggable-next（与 vuedraggable 重复）、mockjs、blueimp-md5、mitt，另有三套图标库并存；③ 后端约 118 处 except Exception，部分静默 pass（suite/tasks.py:81,134），故障会难以定位；④ 无跨机分布式调度，并发上限受 Django-Q 的 workers 配置约束，扩不了机器。

06结论

技术价值真实，资产成熟度不足。

建议按「先治理、再定价值」的顺序推进：

  1. 立刻做两件事：① 给前后端各建 git 仓库并提交全量代码（哪怕只有一个初始 commit，也远好过零历史）；② 轮换 aaa.py 和 .env 里的两个 API Key，删除 aaa.py。这两件事成本极低，但直接决定资产是否「可交付」。
  2. 清理死代码换回真实规模：删掉 35 个模板 demo 页、api/schema.d.ts、components/Http、CountTo 和两个被注释的 plugin。约 7–8 千行，前端规模立刻从「5.5 万行」变成可信的数字，也顺手缩小了打包体积（当前 import.meta.glob 把孤儿页全打进了 dist）。
  3. 把类型检查接进构建：build 脚本加上 vue-tsc --noEmit，打开 noImplicitAny。不用一次性修完 109 处 any，先让它能报错，再按模块收敛。
  4. 把 smart_locator 单独拎出来当成核心资产对待：这是全项目唯一具备差异化壁垒的部分。给它补测试、补文档、把定位策略做成可配置项。如果未来要做技术输出或融资，这是唯一需要重点讲的东西。
  5. 拆分长函数：优先 suite/models.py:344 的 run()（447 行）和 engine.py。这两个是全平台最核心也最难改的地方，改之前务必先有测试覆盖——目前 suite 模块已有 8 个测试文件，基础不错，可以在此基础上加。
