## 2. 部署架构

平台由三个容器组成：

```text
浏览器
  │
  ▼
Nginx（web，80 端口）
  ├── /              → Vue 前端静态文件
  └── /api/          → Django backend:8000
                           │
                           ├── MySQL Unix Socket
                           ├── 日志、截图、上传及执行目录
                           └── Django Q 任务数据

Django Q（scheduler）
  └── 与 backend 共用代码、MySQL 和运行目录
```

三个服务的职责如下：

| 服务 | 职责 | 是否对公网开放 |
| --- | --- | --- |
| `web` | 前端静态资源、SPA 路由、API 反向代理 | 是，80 端口 |
| `backend` | Django API、业务逻辑、执行任务入口 | 否，仅容器网络 |
| `scheduler` | Django Q 定时任务和后台队列 | 否 |

## 3. 部署前准备

### 3.1 服务器最低建议

测试平台会运行浏览器和 UI 自动化任务，资源需求高于普通管理后台。

| 资源 | 最低可运行 | 推荐生产配置 |
| --- | --- | --- |
| CPU | 2 核 | 4 核及以上 |
| 内存 | 2 GB | 4–8 GB |
| Swap | 2 GB | 2–4 GB |
| 磁盘 | 30 GB | 50 GB 及以上 |
| 系统 | Ubuntu 22.04/24.04 | Ubuntu 24.04 LTS |

当前服务器内存约 1.6 GB 且没有 Swap。单任务可以运行，但多个浏览器任务并发时存在内存不足风险，建议上线后补充 Swap 或升级内存。

### 3.2 网络和安全组

在云服务器安全组中放行：

- `22/TCP`：SSH，仅建议允许公司出口 IP；
- `80/TCP`：当前 HTTP 服务；
- `443/TCP`：后续配置 HTTPS 时使用。

不要开放：

- Django 的 `8000` 端口；
- SQLite 文件或任何数据库目录；
- Docker 守护进程端口。

### 3.3 本地源码目录

当前开发机目录：

├── 测试平台后端/
└── 测试平台前端/

后端部署配置：

### 3.4 本地工具要求

## 10. 第七步：初始化 MySQL 并迁移旧数据

生产环境使用服务器现有 MySQL 中的独立数据库 `test_platform`。首次部署可以初始化空库；从旧版本升级时，应先创建表结构，再把 SQLite 业务数据迁移到 MySQL。

### 10.1 MySQL 接入原则

- 不开放公网 3306；
- MySQL 保持只监听服务器本机；
- backend 和 scheduler 通过只读挂载的 `/var/run/mysqld` 目录访问 Unix Socket；
- 使用独立数据库 `test_platform`；
- 使用独立账号 `test_platform@localhost`；
- 账号只授权 `test_platform.*`，不访问服务器上的其他业务库。

### 10.2 创建数据库和账号

使用具备 MySQL 管理权限的系统账号执行：

```bash
sudo mysql
```

在 MySQL 中执行，密码替换为单独生成的强随机值：

```sql
CREATE DATABASE IF NOT EXISTS test_platform
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

CREATE USER IF NOT EXISTS 'test_platform'@'localhost'
  IDENTIFIED BY '替换为数据库专用随机密码';

GRANT ALL PRIVILEGES ON test_platform.*
  TO 'test_platform'@'localhost';

FLUSH PRIVILEGES;
```

退出 MySQL：

```sql
exit
```

不要复用服务器登录密码、MySQL root 密码或 Django 密钥。

### 10.3 验证数据库账号

```bash
mysql \
  --socket=/var/run/mysqld/mysqld.sock \
  --user=test_platform \
  --password \
  test_platform
```

登录后执行：

```sql
SELECT DATABASE(), CURRENT_USER(), VERSION();
```

### 10.5 从 SQLite 迁移业务数据

迁移前先停止会产生写入的服务，并备份源文件和目标库：

```bash
cd /home/deployer/test-platform
docker compose stop web scheduler backend
cp data/db.sqlite3 "data/backups/pre-mysql-switch-$(date +%Y%m%d-%H%M%S).sqlite3"
```

使用临时 SQLite 配置运行 Django 标准导出。内容类型和权限由 MySQL 迁移自动创建，Django Q 已完成任务属于不可跨数据库移植的内部缓存，因此不进入业务数据包；定时计划、套件和用户可见执行报告仍会保留：

```bash
docker compose run --rm --no-deps \
  -e DATABASE_ENGINE=sqlite \
  -e DATABASE_NAME=/source/db.sqlite3 \
  -v "$PWD/data/db.sqlite3:/source/db.sqlite3:ro" \
  -v "$PWD/data/backups:/backup" \
  backend python manage.py dumpdata \
  --natural-foreign --natural-primary \
  --exclude contenttypes \
  --exclude auth.permission \
  --exclude django_q.task \
  --indent 2 \
  --output /backup/sqlite-business-data.json
```

先清空 MySQL 中的初始化数据，再加载业务数据：

```bash
docker compose run --rm --no-deps backend python manage.py flush --noinput
docker compose run --rm --no-deps \
  -v "$PWD/data/backups:/backup:ro" \
  backend python manage.py loaddata /backup/sqlite-business-data.json
```

如果旧后台操作日志引用了已经删除的应用模型，应先通过 `ContentType.objects.get_or_create(...)` 补齐相应内容类型，再执行 `loaddata`。如果旧 Token 不是 DRF 标准的 40 位值，不要扩大数据库字段掩盖异常，应为对应用户重新生成合法 Token 后再导入。

导入后至少核对用户、项目、接口、场景、UI 用例、套件、执行报告、通知配置和定时计划数量，并执行：

```bash
docker compose run --rm --no-deps backend python manage.py check
docker compose run --rm --no-deps backend python manage.py migrate --check
docker compose up -d backend scheduler web
```

旧 `data/db.sqlite3` 和迁移前备份应保留到迁移验收完成；新服务不会再读取它们。

> 2026-08-26 生产迁移记录：316 条可移植对象成功迁入 MySQL；3 个用户、3 个项目、12 个接口、11 个场景、11 个套件、27 条执行报告和 2 条定时计划均完成数量核对。35 条 Django Q 已完成任务内部缓存未迁移，不影响用户可见报告。

## 13. 首次备份

部署完成后创建 MySQL 备份。先读取 `backend.env`，再使用临时客户端配置，避免密码直接出现在进程参数中：

```bash
cd /home/deployer/test-platform
set -a
. ./backend.env
set +a

MYSQL_CNF=$(mktemp)
chmod 600 "$MYSQL_CNF"
printf '[client]\nuser=%s\npassword=%s\nsocket=%s\n' \
  "$DATABASE_USER" "$DATABASE_PASSWORD" "$DATABASE_SOCKET" > "$MYSQL_CNF"

mysqldump \
  --defaults-extra-file="$MYSQL_CNF" \
  --single-transaction \
  --no-tablespaces \
  --routines \
  --triggers \
  --default-character-set=utf8mb4 \
  "$DATABASE_NAME" \
  | gzip > "data/backups/initial-$(date +%Y%m%d-%H%M%S).sql.gz"

rm -f "$MYSQL_CNF"
chmod 600 data/backups/*.sql.gz
```

## 14. 当前部署配置说明

### 14.1 后端镜像

`backend.Dockerfile` 已包含：

- Python 3.11；
- 项目 Python 依赖；
- Gunicorn；
- Chromium；
- ChromeDriver；
- Playwright Chromium；
- 中文字体；

### 14.2 Gunicorn

当前参数：

```text
1 个 Worker + 4 个线程 + 3600 秒超时
```

这是针对当前小内存服务器的保守配置。升级服务器后，可以根据 CPU 和任务模型调整 Worker 数量，但 UI 自动化不应直接无限增加并发。

### 14.3 Nginx

当前配置：

- 上传限制：100 MB；
- API 连接超时：30 秒；
- API 读写超时：3600 秒；
- SPA 路由回退到 `index.html`。

### 14.4 文件保留

`FILE_RETENTION_DAYS=15` 表示执行目录、日志等本地文件默认保留 15 天。数据库中的执行记录是否删除由业务逻辑决定，不应简单等同于文件保留策略。

## 15. 上线后的必要改进

### 15.1 配置 HTTPS

当前使用 HTTP。正式内部使用仍建议：

1. 给服务器绑定域名；
2. 配置 DNS；
3. 使用 Nginx 或云负载均衡配置证书；
4. 把 `REPORT_PUBLIC_BASE_URL` 改为 HTTPS 地址；
5. 把域名加入 `DJANGO_ALLOWED_HOSTS`；
6. 配置安全 Cookie、HSTS 和 CSRF 可信来源。

### 15.2 MySQL 约束检查

当前模型迁移到 MySQL 时会提示两类兼容性注意事项：长唯一字符串索引和带条件的唯一约束。迁移可以完成，但后续应把它们改造成 MySQL 原生可强制执行的索引或应用级校验，避免极端并发下产生重复数据。

### 15.3 Worker 隔离

当前 API 和执行环境共用后端镜像。后续建议将执行 Worker 独立成服务，并为每个任务设置 CPU、内存、浏览器并发和硬超时。
