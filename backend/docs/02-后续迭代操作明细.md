## 2. 迭代发布原则

每次发布必须遵守：

1. 先检查、再备份、后发布；
2. 前端必须使用冻结锁文件构建；
3. 后端模型变更必须有迁移文件；
4. 生产数据库和运行文件永远不放在源码目录；
5. 不修改已有 `DJANGO_SECRET_KEY`；
6. 发布后必须检查 backend、scheduler 和 web；
7. 发布失败时，代码和数据库必须按同一个时间点回滚；
8. 不使用 `docker compose down -v`，它可能删除卷数据；
9. 不对 `/home/deployer/test-platform` 或 `data` 使用 `rsync --delete`；
10. 不在生产机直接修改业务源码，所有改动必须先提交并推送到 GitHub `main` 分支；
11. 发布时记录实际 Git commit，确保可审计、可回滚。

## 3. 每次发布前检查

| 类型 | 是否构建前端 | 是否构建后端镜像 | 是否迁移数据库 |

| 仅前端 | 是 | 否 | 否 |

| 前后端 | 是 | 是 | 视模型变更决定 |

## 4. 发布前备份

### 4.1 设置远程变量

在服务器执行：

```bash
cd /home/deployer/test-platform
STAMP=$(date +%Y%m%d-%H%M%S)
mkdir -p data/backups /home/deployer/releases
```

### 4.2 在线备份 MySQL

```bash
set -a
. ./backend.env
set +a

MYSQL_CNF=$(mktemp)
chmod 600 "$MYSQL_CNF"
printf '[client]\nuser=%s\npassword=%s\nsocket=%s\n' \
  "$DATABASE_USER" "$DATABASE_PASSWORD" "/var/run/mysqld/mysqld.sock" > "$MYSQL_CNF"

mysqldump \
  --defaults-extra-file="$MYSQL_CNF" \
  --single-transaction \
  --no-tablespaces \
  --routines \
  --triggers \
  --default-character-set=utf8mb4 \
  "$DATABASE_NAME" \
  | gzip > "data/backups/pre-release-$(date +%Y%m%d-%H%M%S).sql.gz"

rm -f "$MYSQL_CNF"
chmod 600 data/backups/*.sql.gz
```

`--single-transaction` 可以在 InnoDB 表在线读写时生成一致性备份。备份完成后必须确认文件存在且非 0 字节。

### 4.3 备份当前代码和前端产物

```bash
STAMP=$(date +%Y%m%d-%H%M%S)
tar \
  --exclude='./backend/.git' \
  --exclude='./backend/venv' \
  -czf "/home/deployer/releases/test-platform-code-$STAMP.tar.gz" \
  backend frontend-dist docker-compose.yml nginx.conf
```

记录本次发布：

```bash
printf '%s %s\n' "$STAMP" '本次迭代说明' >> /home/deployer/releases/release-history.log
```

## 9. 修改环境变量

生产变量文件：

```text
/home/deployer/test-platform/backend.env
```

修改前备份：

```bash
cd /home/deployer/test-platform
cp backend.env "backend.env.$(date +%Y%m%d-%H%M%S).bak"
chmod 600 backend.env*
```

修改后重建需要读取变量的容器：

```bash
docker compose up -d --force-recreate backend scheduler
```

环境变量不会因为普通 `docker compose restart` 自动重新加载，因此应使用 `--force-recreate`。

禁止在日常发布时修改：

```text
DJANGO_SECRET_KEY
DATA_ENCRYPTION_KEYS
```

直接替换 `DJANGO_SECRET_KEY` 会导致已有会话、签名数据和部分队列消息失效；直接丢弃旧的 `DATA_ENCRYPTION_KEYS` 会导致已有敏感数据永久无法解密。

### 9.1 开发与生产环境边界

开发环境使用：

```env
DJANGO_ENV=development
DJANGO_DEBUG=true
```

开发模式允许本机调试使用的宽松默认值，可参考 `deploy/backend.env.development.example`，但不得把开发环境变量文件复制到服务器。

生产环境至少必须明确配置：

```env
DJANGO_ENV=production
DJANGO_DEBUG=false
DJANGO_SECRET_KEY=长度不少于50位的强随机值
DATA_ENCRYPTION_KEYS=独立生成的Fernet密钥
DJANGO_ALLOWED_HOSTS=实际域名或服务器IP
DJANGO_CORS_ALLOW_ALL=false
DJANGO_CORS_ALLOWED_ORIGINS=https://实际域名
DJANGO_CSRF_TRUSTED_ORIGINS=https://实际域名
DJANGO_API_DOCS_ENABLED=false
DJANGO_SECURE_SSL_REDIRECT=true
DJANGO_SESSION_COOKIE_SECURE=true
DJANGO_CSRF_COOKIE_SECURE=true
DJANGO_SECURE_HSTS_SECONDS=31536000
```

生产模式会对弱密钥、空主机、通配符主机、调试模式和全开放 CORS 直接拒绝启动。仓库中的 `deploy/backend.env.example` 是生产配置基线，新环境应从该文件复制后填写真实值。

数据库中的服务器密码、私钥口令、数据库密码、环境认证参数和 Token、Prometheus Token、Webhook、接口敏感请求配置、项目变量以及 UI 输入值均使用 `DATA_ENCRYPTION_KEYS` 做字段级静态加密。应用读取时自动解密，API 不返回密码类字段，数据库备份中保存的也是密文。

如果现网仍为纯 HTTP，只能作为过渡方案显式设置：

```env
DJANGO_SECURE_SSL_REDIRECT=false
DJANGO_SESSION_COOKIE_SECURE=false
DJANGO_CSRF_COOKIE_SECURE=false
DJANGO_SECURE_HSTS_SECONDS=0
```

切换 HTTPS 时，要同时更新公开报告地址、允许主机、CORS 来源和 CSRF 可信来源，再重建 backend 与 scheduler 容器。不要只修改其中一项。

### 9.2 安全变量变更检查

每次修改生产安全变量前后，应确认：

1. 来源地址包含协议，且不使用 `*`；
2. 域名和反向代理传递的 Host、HTTPS 协议一致；
3. API 文档入口保持关闭；
4. 密钥未写入 Git、日志、截图或工单；
5. 修改变量后使用 `--force-recreate` 重建容器，而不是普通重启；
6. 若启用 HSTS，必须先确认域名及所覆盖子域均可长期使用 HTTPS。

### 9.3 数据加密密钥轮换

先生成新密钥：

```bash
python3 -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

假设原密钥是 `OLD_KEY`，新密钥是 `NEW_KEY`，轮换时按以下顺序操作：

1. 备份 MySQL 和当前 `backend.env`；
2. 将变量改为 `DATA_ENCRYPTION_KEYS=NEW_KEY,OLD_KEY`，新密钥必须排第一；
3. 重建 backend 和 scheduler，使两个进程同时具备新旧密钥；
4. 先执行只读检查：

```bash
docker compose exec backend python manage.py rotate_data_encryption --dry-run
```

5. 检查通过后执行重新加密：

```bash
docker compose exec backend python manage.py rotate_data_encryption
```

6. 抽查服务器连接、数据库连接、环境认证、告警通知和用例执行；
7. 将变量改为 `DATA_ENCRYPTION_KEYS=NEW_KEY` 并再次重建容器；
8. 将旧密钥转入受控归档，保留到旧数据库备份超过保留期后再销毁。

禁止先删除旧密钥再执行轮换命令。旧备份使用的旧密钥也必须在备份生命周期内保留，否则备份恢复后仍无法读取敏感字段。

## 11. 重新执行和定时任务注意事项

`backend` 与 `scheduler` 共用数据库和 Django 密钥。

发布定时任务相关改动后检查：

```bash
docker compose logs --tail=200 scheduler
```

关注：

- 队列是否持续积压；
- 是否出现 `BadSignature`；
- 是否出现数据库锁；
- Worker 是否反复退出；
- 定时任务是否重复创建；
- 暂停、恢复和重新执行是否更新原记录。

如果更新前有正在运行的测试任务，应优先等待执行完成。必须中断时，要确认统一执行状态机能在异常退出后将任务更新到最终状态，避免永久停留在“执行中”。

## 14. 回滚流程

### 14.1 回滚前原则

代码和数据库迁移存在对应关系。若新版本执行了不可向后兼容的迁移，必须同时回滚代码和数据库。

### 14.2 停止业务写入

```bash
cd /home/deployer/test-platform
docker compose stop backend scheduler web
```

### 14.3 回滚代码包

先查看备份：

```bash
ls -lh /home/deployer/releases/
```

选择正确时间点后：

```bash
tar -xzf /home/deployer/releases/test-platform-code-YYYYMMDD-HHMMSS.tar.gz \
  -C /home/deployer/test-platform
```

### 14.4 回滚数据库

先按第 4.2 节导出当前故障现场，再恢复与旧代码配套的 SQL 备份：

```bash
set -a
. ./backend.env
set +a

MYSQL_CNF=$(mktemp)
chmod 600 "$MYSQL_CNF"
printf '[client]\nuser=%s\npassword=%s\nsocket=%s\n' \
  "$DATABASE_USER" "$DATABASE_PASSWORD" "/var/run/mysqld/mysqld.sock" > "$MYSQL_CNF"

gunzip -c data/backups/pre-release-YYYYMMDD-HHMMSS.sql.gz \
  | mysql --defaults-extra-file="$MYSQL_CNF" "$DATABASE_NAME"

rm -f "$MYSQL_CNF"
```

如果回滚涉及删除新版本创建的表或字段，建议先由 DBA 清空并重建目标库，再导入旧备份，避免新结构残留。

### 14.5 重建和启动

```bash
docker compose build backend scheduler
docker compose up -d
docker compose ps
docker compose logs --tail=100 backend scheduler web
```

### 14.6 回滚验收

- 首页返回 200；
- 登录正常；
- 关键列表正常；
- 数据库记录符合回滚时间点；
- backend 健康；
- scheduler 无持续异常；
- 执行一条低风险 API 用例确认执行链路。

## 15. 常见故障处理

### 15.1 首页打不开

```bash
docker compose ps web
docker compose logs --tail=200 web
curl -I http://127.0.0.1/
sudo ss -lntp | grep ':80'
```

检查安全组、防火墙、80 端口占用及前端 `index.html`。

### 15.2 页面能开但 API 失败

```bash
docker compose ps backend
docker compose logs --tail=200 backend
curl -i http://127.0.0.1/api/project/project/
```

如返回 `502`，检查 backend 健康和 Nginx 容器网络；如返回 `500`，查看 Django Traceback；如返回 `401`，检查登录 Token。

### 15.3 backend 一直不健康

```bash
docker compose logs --tail=300 backend
docker compose run --rm backend python manage.py check
docker compose run --rm backend python manage.py migrate --plan
```

重点检查：

- Python 依赖安装；
- 迁移缺失；
- 数据库权限；
- 环境变量；
- import 错误。

### 15.4 scheduler 报签名错误

如果出现 `BadSignature`：

1. 确认 `DJANGO_SECRET_KEY` 是否被更换；
2. 确认 backend 和 scheduler 使用同一个 `backend.env`；
3. 确认旧签名队列是否仍有待执行数据；
4. 不要直接清队列，先判断是否有业务任务需要保留。

### 15.5 MySQL 连接失败或超时

```bash
systemctl status mysql
ls -l /var/run/mysqld/mysqld.sock
docker compose exec backend ls -l /host/run/mysqld/mysqld.sock
docker compose logs backend scheduler | grep -Ei 'mysql|operationalerror|connection'
```

确认 MySQL 正常、Socket 存在、Compose 已把宿主机 `/run` 挂载到容器 `/host/run`，并检查 `backend.env` 中 `DATABASE_SOCKET=/host/run/mysqld/mysqld.sock`。不要直接挂载会被 MySQL 重建的 `/run/mysqld` 子目录，也不要为了修复连接而把 3306 开放到公网。

### 15.6 UI 用例无法启动浏览器

```bash
docker compose exec backend chromium --version
docker compose exec backend chromedriver --version
docker compose exec backend python -m playwright --version
```

Selenium：优先检查配置的 ChromeDriver 路径及主版本；本地无匹配版本时才会使用 Selenium Manager。Playwright：检查浏览器安装目录和依赖。

### 15.7 UI 用例执行慢或进程被杀

```bash
free -h
docker stats --no-stream
dmesg | grep -i -E 'killed process|out of memory'
```

处理顺序：

1. 降低 UI 任务并发；
2. 清理残留浏览器进程；
3. 增加 Swap；
4. 升级内存；
5. 将 UI Worker 拆分到独立机器。

### 15.8 上传或截图返回 401

检查前端请求是否携带认证 Token，以及资源接口是否使用了与普通 API 相同的认证方式。不要通过开放匿名权限绕过问题。
